# 🏗️ project.md: hosting.app (Суверенний Серверний Менеджер)

## 🧭 Фаза 1: Філософія та Абстракція (The Seed)

### 1. Mission and Philosophy (aaPanel Context & Constraints)
Традиційні панелі керування серверами (такі як aaPanel) страждають від критичних архітектурних вад:
* **Приховані runtime-збої та баги поштової системи:** Жорсткий хардкод валідації (наприклад, обов'язковість локального MX/PTR для додаткових доменів замість єдиного інфраструктурного ядра) призводить до збоїв SSL або некоректної доставки пошти.
* **Монолітна прив'язка до одного веб-сервера:** Неможливість легко замінити веб-сервер або гнучко перемикатися між ними без ручного переписування багатьох системних скриптів.
* **Відсутність адекватної API-оркестрації:** Зміни в конфігураціях вимагають перезапуску сервісів замість динамічного оновлення через API.

**hosting.app** — це повнофункціональний суверенний менеджер хостингу, який виходить далеко за рамки звичайного поштового сервера і охоплює:
1. **Керування веб-сайтами (Web Hosting):** Створення сайтів, реверс-проксі бекендів (Node.js, Go, Python тощо) та статичного хостингу.
2. **Керування поштою (Mail Server):** Інфраструктура поштових доменів та скриньок.
3. **CDN, DNS та Кешування:** Інтеграція з Cloudflare/BunnyCDN для синхронізації записів і управління кеш-тегами.

### 2. Абстракція веб-серверів та вибір Caddy
Для забезпечення гнучкості хостинг будується на принципі **інтерчейндж адаптерів** (`BaseWebServerAdapter`). Це дозволяє реалізувати підтримку будь-якого веб-сервера:

* **Caddy (Основний вибір за замовчуванням):**
  * *Переваги:* Має вбудоване автоматичне отримання Let's Encrypt SSL сертифікатів без сторонніх скриптів (certbot). Надає потужний dynamic JSON-API, що дозволяє додавати та змінювати хости на льоту без перезапуску процесу.
  * *Недоліки:* За результатами тестів продуктивності Caddy показує приблизно на **15% вищу затримку (latency)** порівняно з екстремально швидким Nginx.
* **Nginx (Альтернативний адаптер):**
  * *Переваги:* Максимальна швидкість віддачі статики та обробки з'єднань.
  * *Недоліки:* Складніше налаштування динамічного керування конфігами без рестартів сервісу.

Логіка `hosting.app` проєктується так, що ядро Runner викликає методи адаптера (`addDomain`, `removeDomain`). Поточна MVP реалізація стартує з адаптера Caddy для максимальної простоти автоматизації та надійності SSL, але архітектура готова до швидкого підключення Nginx-адаптера.

## 📐 Фаза 2: Доменне Моделювання (Data-Driven Models)

Схеми даних описують повний спектр хостинг-послуг (файли в `src/domain/`):

1. **`WebDomainSchema` (Керування веб-сайтами):**
   * Описує домени, шлях до кореня сайту (`root`), статус активності, SSL конфігурацію та порт внутрішнього реверс-проксі (`proxy_port`).
2. **`MailServerSchema` (Поштова інфраструктура):**
   * Задає параметри поштового домену, розміри ключів DKIM, селектори та спам-фільтри (Rspamd).
3. **`MailboxSchema` (Поштові скриньки):**
   * Описує скриньки, ліміти дискових квот, паролі та переадресацію.
4. **`CdnSyncSchema` (Налаштування CDN):**
   * Керує токенами доступу до CDN та статусом проксіювання.

### 3. Логіка розумної валідації пошти та Blacklist API
На відміну від багів aaPanel, `hosting.app` реалізує математично точну модель перевірки DNS-записів для мультиорендних серверів:

#### А. Валідація MX (Mail Exchange)
* **Проблема aaPanel:** Вимагає, щоб MX запис кожного домену вказував виключно на його власний піддомен (наприклад, `mail.tenant.com`), інакше показує помилку.
* **Рішення hosting.app:** Система перевіряє MX-запис домену `tenant.com`. Якщо він вказує на будь-який хост (наприклад, `mail.eaukraine.eu`), система робить резолв цього хоста. Якщо отримана IP-адреса збігається з IP нашого сервера (`142.132.174.234`), статус MX маркується як **OK**. Це дозволяє використовувати єдине інфраструктурне ядро для всіх клієнтських доменів.

#### Б. Валідація PTR (Зворотний DNS)
* **Проблема aaPanel:** Намагається перевірити PTR-запис для кожного домену окремо, що є технічно неможливим, оскільки одна IP-адреса може мати лише один PTR-запис.
* **Рішення hosting.app:** Система перевіряє PTR-запис виключно для поточної IP-адреси сервера. Якщо PTR-запис (наприклад, `mail.eaukraine.eu`) резолвиться назад в IP нашого сервера (Forward-Confirmed Reverse DNS), статус PTR вважається **валідованим для всіх доменів на цьому сервері**.

#### В. Валідація SPF
* Перевіряється наявність у TXT записі домену директиви `mx` (яка делегує дозвіл перевіреному нами MX-серверу) або безпосередньої IP-адреси нашого сервера.

#### Г. Валідація DKIM
* Система виконує DNS-запит TXT-запису за шляхом `{selector}._domainkey.{domain}`. 
* Отримане значення парситься для перевірки наявності версії `v=DKIM1` та наявності поля публічного ключа `p=`. Якщо запис знайдено та успішно верифіковано — статус маркується як **OK**.

#### Ґ. Валідація DMARC
* Виконується DNS-запит TXT-запису за шляхом `_dmarc.{domain}`.
* Отримане значення парситься для перевірки наявності версії `v=DMARC1` та тегу політики `p=` (наприклад, `p=none`, `p=quarantine` або `p=reject`).

#### Д. Інтеграція Blacklist Monitor API
* Утиліта фонового моніторингу періодично робить паралельні DNS-запити до списку світових RBL (Spamhaus, Barracuda, Spamcop тощо) для IP-адреси сервера.
* При виявленні хоста в чорних списках система миттєво генерує сповіщення через API та виводить попередження в адмін-панель.

## 🛠 Фаза 3: Верифікація Логіки (CLI-First)

Уся логіка управління конфігурацією хостингу та веб-сервера повністю працездатна через консольний інтерфейс. Будь-які дії з підняття сайтів, перевірки працездатності проксі та DNS тестуються через автоматичні Snapshot-тести.
