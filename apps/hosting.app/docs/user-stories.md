# User Stories: hosting.app (Сценарії використання)

Цей документ містить канонічні сценарії використання для автоматизованого контрактного тестування інтерфейсу (OLMUI Story Testing).

---

## 🌐 Розділ 1: Керування веб-доменами (Web Domains)

### Story 1: Додавання нового статичного домену з автоматичним DNS
- **Роль**: Системний адміністратор.
- **Мета**: Приєднати новий сайт та налаштувати його локальну папку.
- **Сценарій**:
  1. Користувач запускає додаток та обирає дію "Додати Веб-сайт".
  2. Система запитує домен за схемою `WebDomainSchema` (вводиться `my-portfolio.page`).
  3. Система перевіряє доступність шляху `/www/wwwroot/my-portfolio.page` і створює його.
  4. Система перезапускає Nginx та повідомляє про успішне налаштування.

### Story 2: Налаштування реверс-проксі для Node.js додатка
- **Роль**: Веб-розробник.
- **Мета**: Перенаправити трафік з домену на локальний порт 3000.
- **Сценарій**:
  1. Користувач обирає домен `my-portfolio.page` та редагує його налаштування.
  2. У полі `proxy_port` вказує значення `3000`.
  3. Система перевіряє валідність порту, створює конфігурацію Nginx з директивою `proxy_pass http://127.0.0.1:3000`.
  4. Перевіряє конфігурацію Nginx (`nginx -t`) та перезавантажує сервіс.

### Story 3: Автоматичний випуск Let's Encrypt SSL сертифікату
- **Роль**: Користувач.
- **Мета**: Захистити з'єднання через HTTPS.
- **Сценарій**:
  1. Користувач перемикає опцію `ssl_provider` у значення `Let's Encrypt`.
  2. Система перевіряє, чи спрямовує DNS-запис домену на поточний IP сервера.
  3. Система запускає Acme-клієнт, генерує сертифікат та підключає його в конфіг Nginx.

### Story 4: Вимкнення та архівація домену
- **Роль**: Адміністратор.
- **Мета**: Тимчасово зупинити обслуговування сайту.
- **Сценарій**:
  1. Користувач знімає галочку з опції `active` для домену `my-portfolio.page`.
  2. Система вимикає конфіг Nginx та замінює його на дефолтну заглушку "Site Offline".

### Story 5: Видалення домену зі збереженням логів
- **Роль**: Адміністратор.
- **Мета**: Повністю видалити домен, але зберегти аналітику.
- **Сценарій**:
  1. Користувач ініціює видалення домену.
  2. Система запитує підтвердження: "Видалити файли сайту?". Користувач обирає "Ні, зберегти файли".
  3. Система видаляє конфігурацію Nginx, очищує записи в базі SQLite, але залишає папку `/www/wwwroot/` недоторканою.

## 📧 Розділ 2: Керування поштовим сервером (Mail Server & DKIM)

### Story 6: Ініціалізація поштового сервера для домену
- **Роль**: Системний адміністратор.
- **Мета**: Налаштувати Dovecot, Postfix та Rspamd для роботи з новим доменом.
- **Сценарій**:
  1. Користувач обирає дію "Налаштувати Поштовий Сервер".
  2. Вводить поштовий домен `yaro.page`.
  3. Система перевіряє наявність користувача `vmail` та створює для нього підпапку `/www/vmail/yaro.page`.
  4. Записує поштові правила в конфігурацію postfixadmin SQLite.

### Story 7: Генерація та підключення DKIM підпису
- **Роль**: Системний адміністратор.
- **Мета**: Запобігти потраплянню листів у спам через налаштування DKIM.
- **Сценарій**:
  1. Система автоматично генерує пару ключів для домену `yaro.page` за допомогою утиліти `rspamadm dkim_keygen`.
  2. Записує приватний ключ у `/www/server/dkim/yaro.page/default.private`.
  3. Оновлює конфігурацію Rspamd `/etc/rspamd/local.d/dkim_signing.conf`, додаючи блок для `yaro.page`.
  4. Виводить публічний ключ у зручному форматі TXT-запису для DNS.

### Story 8: Активація поштової скриньки
- **Роль**: Користувач.
- **Мета**: Створити першу робочу адресу на власному домені.
- **Сценарій**:
  1. Користувач обирає поштовий домен `yaro.page` та натискає "Створити скриньку".
  2. Вводить ім'я скриньки `admin` (отримуємо `admin@yaro.page`) та безпечний пароль.
  3. Система генерує пароль у зашифрованому вигляді SHA512-CRYPT.
  4. Створює запис у таблиці `mailbox` та створює поштову директорію для Maildir.

### Story 9: Налаштування переадресації (Email Forwarding)
- **Роль**: Користувач.
- **Мета**: Отримувати копії листів на особистий Gmail.
- **Сценарій**:
  1. Користувач відкриває редагування скриньки `admin@yaro.page`.
  2. У полі `forward_to` вказує адресу `my-personal-email@gmail.com`.
  3. Система перевіряє валідність адреси та записує правило переадресації в таблицю `alias`.

### Story 10: Зміна квоти дискового простору скриньки
- **Роль**: Адміністратор.
- **Мета**: Обмежити дисковий простір для скриньки користувача.
- **Сценарій**:
  1. Адміністратор обирає скриньку `admin@yaro.page` і повзунком `quota_bytes` встановлює ліміт на `10 GB`.
  2. Система перераховує гігабайти в байтовий еквівалент та оновлює запис у базі даних Dovecot SQLite.

## ☁️ Розділ 3: Інтеграція CDN та резервного копіювання

### Story 11: Синхронізація сайту з Cloudflare CDN
- **Роль**: Веб-розробник.
- **Мета**: Увімкнути кешування та захист від DDOS через API.
- **Сценарій**:
  1. Користувач обирає домен `my-portfolio.page` та відкриває вкладку "CDN".
  2. Обирає провайдера "Cloudflare" та вводить свій `api_token`.
  3. Система зв'язується з Cloudflare API, перевіряє DNS-записи та перемикає статус проксіювання (увімкнено помаранчеву хмаринку).

### Story 12: Очищення кешу на CDN (Purge Cache)
- **Роль**: Веб-розробник.
- **Мета**: Миттєво показати користувачам оновлений дизайн сайту.
- **Сценарій**:
  1. Користувач після оновлення файлів натискає кнопку "Очистити кеш CDN".
  2. Система надсилає POST-запит до API Cloudflare з командою `purge_everything`.
  3. Показує користувачеві прогрес-бар та сповіщає про завершення.

### Story 13: Автоматичний бекап бази даних пошти
- **Роль**: Системний адміністратор.
- **Мета**: Захистити поштові скриньки від втрати даних.
- **Сценарій**:
  1. Користувач налаштовує щоденне завдання резервного копіювання.
  2. Система кожні 24 години робить дамп SQLite бази даних `/www/vmail/postfixadmin.db`.
  3. Архівує її разом із поштовими скриньками `/www/vmail/` та зберігає в локальну резервну папку.

### Story 14: Перевірка здоров'я сервісів (Health Check Dashboard)
- **Роль**: Системний адміністратор.
- **Мета**: Моніторити роботу веб-сервера та пошти в реальному часі.
- **Сценарій**:
  1. Користувач відкриває консоль моніторингу `hosting.app`.
  2. Система перевіряє статус процесів Nginx, Dovecot, Postfix та Rspamd.
  3. Перевіряє рівень використання оперативної пам'яті (RAM) та диска.
  4. Візуально рендерить зелені/червоні індикатори статусу для кожного сервісу.

### Story 15: Інтеграція з editor.app для швидкого редагування файлів конфігурації
- **Роль**: Веб-розробник.
- **Мета**: Відкрити конфігураційні файли Nginx безпосередньо в інтегрованому редакторі коду.
- **Сценарій**:
  1. Користувач натискає кнопку "Редагувати конфіг Nginx" для сайту `my-portfolio.page`.
  2. `hosting.app` відправляє інтенцію запуску `editor.app`, передаючи шлях до файлу конфігурації.
  3. Редактор коду завантажує файл у вкладку і дозволяє його редагувати зі збереженням на сервері з перевіркою конфігу (`nginx -t`).
