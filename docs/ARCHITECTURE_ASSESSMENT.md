# Оценка архитектуры Model-as-App / OLMUI

## Краткий вывод

Система имеет смысл как специализированный слой для переиспользования последовательных пользовательских сценариев между Web, CLI, headless и, потенциально, чат-интерфейсами. Как универсальную архитектуру приложений её пока не стоит позиционировать.

Итоговая рекомендация: **narrow adopt** — продолжать развивать и применять там, где один сценарий действительно должен жить в нескольких интерфейсах.

| Критерий | Оценка |
|---|---:|
| Концептуальная цельность | 8/10 |
| Польза для последовательных multi-UI сценариев | 8/10 |
| Пригодность как общая архитектура приложений | 4/10 |
| Зрелость реализации | 5–6/10 |
| Оригинальность комбинации | 6/10 |
| Оригинальность отдельных механизмов | 2–3/10 |

Это ориентировочные экспертные оценки, а не измеренные метрики.

## Что здесь действительно ценно

Система объединяет три идеи:

1. `Model-as-Schema`: метаданные модели используются для валидации, форм и CLI.
2. `Model-as-App`: приложение представлено async generator, который выдаёт `ask`, `show`, `progress`, `render`, `result` и получает ответы адаптера.
3. OLMUI: один и тот же сценарий исполняется разными интерпретаторами — Web, CLI или headless.

Это не только описание на бумаге. В `src/domain/app/HabitApp.js` действительно находится общий сценарий, `packages/ui/src/core/GeneratorRunner.js` интерпретирует intents, а CLI и Web подключают свои обработчики.

Главная выгода — переиспользуется не только бизнес-логика, но и **порядок взаимодействия**: что спросить, когда проверить, когда сохранить, что показать и какой structured result вернуть. Обычный shared domain layer этого сам по себе не даёт.

Особенно хорошо система подходит для:

- onboarding и setup wizard;
- административных и CRUD-операций;
- установщиков и approval flows;
- developer tools с Web + CLI;
- agent/chat-интерфейсов;
- коротких линейных бизнес-процессов.

Async generator здесь очень уместен: сценарий читается сверху вниз, `yield*` даёт естественную композицию дочерних приложений, а `try/catch/finally` — понятную обработку ошибок и отмены.

Положительный сигнал даёт и эксперимент: 30 сценариев дали 26/26 совпадающих результатов и 11/11 совпадающих состояний между интерфейсами. Изменение правила `80 → 60` потребовало правки одного production policy-файла и ни одного policy-изменения в CLI или Web. Основные domain/model-app/architecture проверки также проходят: 147/147.

## Чем система отличается от общепринятых подходов

| Подход | Сходство | Отличие OLMUI |
|---|---|---|
| Hexagonal / Ports & Adapters | Ядро не зависит от UI и БД | OLMUI превращает входной порт в двусторонний поток UI-intents и переиспользует сам диалог, а не только use case. Но основная цель UI/DB independence уже сформулирована в [Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/). |
| Redux-Saga / effect DSL | Generator выдаёт декларативные инструкции, интерпретатор исполняет и возобновляет его | Механика близка к [Redux-Saga declarative effects](https://redux-saga.js.org/docs/basics/DeclarativeEffects/), но здесь она поднята до уровня полного пользовательского journey. У Saga значительно богаче concurrency: `all`, `race`, `fork`, `cancel`. |
| Elm / Redux / MVU | Однонаправленное взаимодействие и отделение логики от представления | В [Elm Architecture](https://guide.elm-lang.org/architecture/) состояние и переходы явны. Здесь состояние частично спрятано в continuation генератора: линейный сценарий проще, но reload, back, deep link и параллельные события сложнее. |
| Schema-driven UI | Формы генерируются из схемы | Это уже распространено, например в [JSON Forms](https://jsonforms.io/docs/). Отличие — соединение schema-driven UI с orchestration, CLI и headless execution. |
| Statecharts / XState | UI-flow отделяется от конкретного UI | [XState](https://stately.ai/docs) делает состояния, переходы, параллелизм и snapshots явными. OLMUI заметно компактнее для линейного flow, но хуже подходит для восстановления процесса и сложной навигации. |

По критериям глубины модулей, локальности изменений и стоимости интерфейсов сильнее всего выглядит `HabitStore`: маленький интерфейс `load/save` скрывает существенную сложность persistence — это действительно глубокий модуль.

Сам `ModelAsApp`, наоборот, имеет гораздо больший фактический контракт, чем кажется: metadata, aliases, response envelopes, семь видов intents, lifecycle, validation и capability assumptions. Поэтому его интерфейс пока нельзя назвать особенно маленьким или глубоким.

## Ограничения

- Для одного интерфейса накладные расходы, скорее всего, не окупятся. Conventional application service + ports/adapters даст большую часть пользы дешевле.

- Это не буквально «один UI». Переиспользуется orchestration, но Web всё равно требует компонентов, accessibility, navigation, persistence bridge и E2E; CLI — prompts, streams и formatting.

- Generator continuation нельзя нормально сериализовать. После reload нельзя просто восстановить середину сценария. История браузера, deep links, undo и долгоживущие workflows потребуют checkpoint/state-machine слоя.

- Для dashboards, editors, games, realtime collaboration и множества независимых событий линейный generator становится неудобным. Там MVU, actors или statecharts обычно естественнее.

- В domain уже просачивается presentation vocabulary: например `render('Table')` в `HabitStatusApp.js`. Лучше выдавать семантические данные, а решение «таблица это или карточки» оставлять адаптеру.

- В репозитории пока есть несколько несовместимых runner/hook реализаций. Это признак того, что протокол ещё не стал стабильной платформой.

- Самый серьёзный production-риск — Web отправляет на сервер целый документ состояния, а сервер после структурной проверки сохраняет его целиком. Нет server-side повторного применения business rules, версии/CAS и защиты от lost update. Для локального single-user demo это нормально; для multi-user приложения — нет.

Текущий внутренний `REJECT` в `EFFECTIVENESS.md` не следует считать провалом архитектуры. Это fail-closed verdict из-за незаполненной evidence-строки atomicity. При этом человеческая usability пока действительно не проверена: 0 из 5 участников и 0 из 30 попыток. Прототип доказывает техническую осуществимость и locality, но ещё не экономию времени или превосходство над альтернативами.

## Насколько это оригинально

**Оригинальны название, упаковка и конкретный синтез. Не оригинальны базовые механизмы.**

OLMUI/Model-as-App удачно соединяет:

- Hexagonal Architecture;
- generator-based effect interpreters;
- schema-driven UI;
- application workflows;
- композицию через `yield*`.

Такая комбинация достаточно характерная, чтобы стать собственным архитектурным паттерном или библиотекой. Но это не новый вычислительный принцип и не архитектура «без аналогов». Утверждение об отсутствии мировых аналогов в `docs/analysis.md` лучше заменить на:

> Distinctive synthesis of generator-driven workflows, schema-derived interaction and ports/adapters.

## Рекомендации

1. Позиционировать OLMUI как опциональный **application-journey layer**, а не как замену всей архитектуры.
2. Перевести сервер с сохранения целого документа на команды `AddHabit`, `CheckInHabit` с server-side policy, versioning и транзакциями.
3. Оставить один canonical runner и оформить intents как версионированный discriminated protocol с явными capabilities.
4. Добавить опциональные сериализуемые checkpoints/statechart для reload и долгих flows.
5. Реализовать второе, принципиально другое приложение и сравнить стоимость: обычный application layer против OLMUI при одном, двух и трёх интерфейсах.

## Итог

Это осмысленная и интересная архитектурная специализация с хорошим потенциалом для линейных multi-UI приложений. Она оригинальна как инженерный синтез, но не как новая фундаментальная парадигма. Текущая реализация доказывает feasibility, пока не superiority.
