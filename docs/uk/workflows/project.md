# 🏗️ Ворклоу: Project Architecture (project.md)

Цей workflow визначає правила документування **архітектури** та управління станом завдань (PM-as-Code) для кожного пакету чи додатку в екосистемі `nan0web`.

## 1. Розділення Документації

Для чіткого розуміння контексту як розробниками, так і AI-асистентами, документація поділяється за своїм призначенням:

- 📖 **`README.md` (Public Docs & Usage)**
  - Призначення: Технічна інструкція з використання (API пакету, як викликати функції).
  - Спрямована на розробників-споживачів пакету.
  - Часто генерується автоматично з тестів (`src/README.md.js`) з використанням `docs-site` підходу.

- ⚙️ **`project.md` (Architecture Overview & Router)**
  - Призначення: Глибоке пояснення того, **як саме** працює цей пакет зсередини, його внутрішня структура, патерни, архітектурний задум та прив'язка до PM-as-Code.
  - Спрямований на розробників та AI агентів, які будуть **вдосконалювати чи розширювати поточний пакет**.

- 🎯 **`releases/**/*.md` (PM-as-Code: Завдання та Трекінг)**
  - Призначення: Першоджерело правди для задач, чеклістів, контрактних тестів (`task.spec.js` / `task.test.js`) та метрик часу.
  - Це не просто статичні нотатки — це живі специфікації завдань, що відстежуються через `nan0release check` та веб-панель.

## 2. Обов'язковість, Локалізація та Frontmatter

- **Обов'язковість**: КОЖЕН окремий пакет в монорепозиторії (у папках `packages/` чи `apps/`) **МАЄ МАТИ** файл `project.md` в своєму корні як роутер, і переклади в `docs/uk/project.md` та `docs/en/project.md`.
- **YAML Frontmatter (Для Indexator)**: Кореневий файл `project.md` ПОВИНЕН починатися з метаданих для надшвидкого парсингу екосистемним індексатором без використання ШІ:

  ```yaml
  ---
  description: Короткий опис архітектурного призначення пакету.
  tags: [ui, cli, router]
  ---

  # 🏗️ Architecture

  - [🇺🇦 Українська (Оригінал)](./docs/uk/project.md)
  - [🇬🇧 English (Translation)](./docs/en/project.md)
  ```

- **Мова оригіналу**: Основний `project.md` обов'язково пишеться українською мовою і розміщується за шляхом `docs/uk/project.md`.
- **Копія Англійською**: Точний переклад архітектурного документу розміщується за шляхом `docs/en/project.md`.

## 3. Пріоритети та PM-as-Code

Для ефективного фокусування розробки та закриття технічного боргу використовується числова шкала пріоритетів:

| Рівень | Назва | Опис та сценарій застосування |
|:------:|:-----:|-------------------------------|
| **0** | `P0` (Critical) | Найвищий критичний пріоритет (наприклад, ядра платформи: bank, eaukraine.eu, ipne.ws, release). Робота ведеться в першу чергу. |
| **1** | `P1` (High) | Високий пріоритет. Активні пакети в поточному спринті з відкритими контрактами. |
| **2** | `P2` (Medium) | Стандартний пріоритет. Стабільні бібліотеки або планові поліпшення. |
| **3** | `P3` (Low / Backlog) | Низький пріоритет. Фоновий беклог або заморожені експерименти. |

### Збереження стану (Persistence)
- **Першоджерело у репозиторії:** Базові пріоритети та статус релізу фіксуються в frontmatter відповідного `releases/.../release.md` або `project.md` (`priority: 0`).
- **Клієнтський стан (Браузер):** Інтерактивні зміни пріоритетів розробником у веб-дашборді (`nan0release web`) зберігаються локально через адаптер бази даних `this.$db` (IndexedDB / Local Database).
- **Синхронізація:** Локальні перемикання залишаються в браузері розробника для гнучкого фокусування. За потреби зафіксувати новий пріоритет для всієї команди, розробник оновлює поле `priority` у відповідному markdown-документі та робить git commit.

## 4. Структура `project.md` (За Універсальним Шаблоном 5 Фаз)

Створюючи `project.md`, ви спираєтеся на еталонний шаблон: **../universal-project.md**:

1. **Фаза 1: Філософія та Абстракція (The Seed)**
   - Фундаментальна місія пакету.
   - Базова абстракція та глосарій (термінологія).
2. **Фаза 2: Доменне Моделювання (Data-Driven Models)**
   - Опис моделей (`src/domain/*.js`) як схем даних (Model-as-Schema).
   - Використання метаданих (`help`, `type: "text/markdown"` тощо).
   - Як цей пакет інтегрується з `ui-cli`. Консольні сценарії та команди.
3. **Фаза 3: Контракти та TDD**
   - Контрактні тести у `releases/**/*.spec.js`.
4. **Фаза 4: Sovereign Workbench (The Master IDE)**
   - Реєстрація моделей в пісочниці пакету (`play/`).
   - Інтеграція SSG-документації в UI пісочниці.
5. **Фаза 5: Тематизація та Інтерфейс (Theming)**
   - Base UI, CSS Custom Properties, відокремлення логіки від бренду.

## 5. Інструкція для Агентів

Перед масштабним рефакторингом у будь-якому пакеті:
1. Знайдіть і ПОВНІСТЮ прочитайте `project.md`.
2. Якщо `project.md` відсутній — запропонуйте створити його за цим стандартом.
