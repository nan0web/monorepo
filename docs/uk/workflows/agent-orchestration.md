## 🤖 Матричний Конвеєр (Matrix Orchestration Pipeline)

Це фундаментальний пайплайн екосистеми Zero-Hallucination. Його мета — розбити складну задачу на атомарні, ізольовані кроки, які виконуються без контекстного шуму, з обов'язковою інспекцією до і після. **Очікування (Expectations) = Definition of Done**.

### 1. Seeding (Зародження Наміру)

- **Необхідні файли на вхід:** Перед початком створення будь-чого агент ОБОВ'ЯЗКОВО має перевірити `nan0web/packages/index.md` або `nan0web/apps/index.md` для аналізу існуючих рішень (щоб уникнути дублювання пакетів чи функціоналу).
- **Суть:** Всі завдання починаються зі створення або оновлення `seed.md` у цільовому пакеті. Жодних дій "на льоту".
- **Процес:** Ідея аналізується та перетворюється в ТЗ з чіткими "Очікуваннями". Дивись [`app-pipeline-01-seed.md`](./app-pipeline-01-seed.md).
- **Артефакт:** Документ `seed.md` із зафіксованим Definition of Done.

### 2. Розподілені Матриці (Distributed Workflows & Inspectors)

- **Децентралізація:** В екосистемі OLMUI воркфлоу та інспектори більше не зберігаються в одному централізованому місці. Вони розподілені по відповідних пакетах.
- **Жорсткий Експорт (nan0web.nan0):** Щоб уникнути "магічного сканування", кожен пакет **явно декларує** своїх агентів (їхні воркфлоу та інспектори) у конфігураційному файлі `nan0web.nan0`. Один запис в `nan0web.nan0` = один Агент.
- **Генерація Індексу Агентів:** CLI `nan0ai index` проходить по `nan0web_store.csv`, зчитує всі `nan0web.nan0` і генерує єдиний глобальний індекс доступних Агентів у мережі.
- Коли Архітектор планує розробку, він підтягує інструкції виключно з цього жорсткого згенерованого індексу.

### 3. Матрична Декомпозиція (Matrix Breakdown)

- **Суть:** Намір із `seed.md` розбивається на атомарні підзадачі за їхньою структурою.
- **Матриці Розподілу:** Кожна підзадача маршрутизується через 3 осі:
  - **1. Матриця Агентів (Agents Matrix):** Хто фізично вносить зміни? (вибирається з індексу `nan0ai`).
  - **2. Матриця Workflow (Rules Matrix):** За якими правилами діє агент? (підтягується з відповідного пакета).
  - **3. Матриця Інспекторів (Inspectors Matrix):** Чим ми перевіряємо результат? (запускаються інспектори з різних пакетів).

### 4. Ізольоване Виконання (Isolated Context & Parallelism)

- **Обмеження контексту (Zero-Hallucination Context):** Агенту, що виконує підзадачу, передається **тільки той код**, який потрібен для цієї задачі (`context_files`). Якщо задача стосується UI-кнопки, агент не бачить логіку бази даних.
- **Паралелізм:** Якщо `context_files` різних підзадач не перетинаються, Оркестратор запускає їх паралельно (`Promise.all`).

### 5. Інспекція: Pre-flight & Post-flight Checks

- **Pre-flight:** Перед будь-якими змінами запускається інспектор, щоб зафіксувати чистий базовий стан.
- **Post-flight:** Після змін інспектор запускається повторно. Якщо тест падає, агент має змогу отримати помилку та виправити її (Retry loop).

### 6. Принцип "Лише Нові Зміни" (One Task = One Release)

- **Суть:** Заборонено вносити правки у вже завершений код з попередніх кроків у межах однієї ітерації. Це запобігає зацикленням.
- **Реліз:** Щойно інспектор підтвердив успіх, Оркестратор робить атомарний коміт: `git commit -m "feat(matrix): [subtask-name] done"`.

### 7. Фінальний Definition of Done (DoD)

- Задача вважається завершеною тільки тоді, коли результати роботи всіх інспекторів та фінального рендеру на 100% відповідають зафіксованим Очікуванням із `seed.md`. Ні кроком менше.
