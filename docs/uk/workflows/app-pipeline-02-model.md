# 🏭 `app-pipeline-02-model`

> **Призначення:** Другий крок створює `Model-as-Schema` класи. Вхідними даними завжди є `seed.md` (або `user-stories.md`), згенеровані на попередньому кроці. Цей workflow генерує JS/TS файли в `src/domain/*.js`.

## Інструкція для Агента

Коли Користувач запускає цей workflow, ти маєш проаналізувати вхідний `seed.md` або `user-stories.md` і виконати наступні дії:

1. **Ідентифікація Сутностей:**
   - Знайди всі згадані в `seed.md` поля та абстракції. 
   - Створи потрібну кількість `*Model` класів (наприклад `WorkflowModel.js`, `ChatModel.js`).

2. **Правила `Model-as-Schema`:**
   Кожна модель ПОВИННА слідувати суворому формату `Model-as-Schema` (`/model-schema`).
   - Будь-яке поле, що має UI-значення, описується як `static field = { default: ..., type: '...', validate: () => {} }`.
   - Всі повідомлення про помилки та UI-тексти **обов'язково** зберігаються у об'єкті `static UI = { ... }`.
   - ЖОДНИХ захардкоджених текстів всередині конструкторів чи методів. Все має братись із `Class.UI.key_name`.
   - Метод `async *run()`(генератор) використовується ДЛЯ БІЗНЕС-ЛОГІКИ, повертаючи інтенції `ask()`, `progress()`, `log()`. 
   - **Обов'язкова типізація (JSDoc):** Усі властивості інстансу типізуються **ВИКЛЮЧНО** всередині конструктора через `/** @type {Type} */ this.field`.
   - ❌ **ЗАБОРОНЕНО** використовувати class fields (напр. `field = ...`), щоб не перезаписувати дані, передані в `super(data, options)`.

3. **Створення файлів:**
   - Усі моделі розміщуються виключно в теці `src/domain/`.
   - Використовуй сучасний ESM синтаксис (`export class`).

4. **Додавання Test Hook (Story):**
   - У фінальному файлі обов'язково імпортуй ініціалізацію для історій `src/domain/Модель.story.js` (якщо така передбачена архітектурою).

## Завершення:
Після збереження всіх `*.js` файлів у `src/domain/`, запропонуй Користувачу відкрити НОВИЙ чат і запустити `/[app-pipeline-03-contract]` для написання прив'язаних тестів до згенерованих User Stories.
