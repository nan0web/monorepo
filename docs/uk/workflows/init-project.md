# `init-project` Workflow (Zero-Hallucination Sovereign Engine)

> **Призначення:** Єдиний базовий протокол для розгортання або адаптації проєкту під суворі інженерні стандарти **0HCnAI** (Agnostic AI API, OLMUI, Model-as-Schema).

Цей workflow працює універсально: якщо директорія порожня (новий проєкт) — він розгорне новий. Якщо проєкт вже існує (старий код) — він спершу проведе аудит існуючої бази, адаптує та оновить їх до нових стандартів.

## Крок 1: Встановлення Агента

Перед ініціалізацією або адаптацією інфраструктури, переконайся, що у поточному проєкті присутня папка агента (`.agent/`) та базовий `nan0web.config.yaml` / `system.md`.

Якщо їх немає, запусти команду для копіювання/оновлення агентів із фреймворку:

// turbo

```bash
npx 0hcnai agent --merge
```

_(або `node /Users/i/src/nan.web/packages/0HCnAI.framework/bin/generate.js agent --merge`)_

## Крок 2: Діалог Суверена (The Seed)

**ЗАБОРОНЕНО** генерувати будь-який код, поки не буде проведений аналіз та діалог із користувачем.

Якщо проєкт:

- **НОВИЙ:** Постав користувачу 3 обов'язкових запитання (Місія, Абстракція/суть, Обмеження). Створи файл `seed.md`.
- **ІСНУЮЧИЙ:** Проскануй наявну структуру, файли `package.json` та вихідні тексти. Зрозумівши суть системи, запитай користувача, що конкретно ми залишимо (наприклад, який дизайн чи бізнес-логіку), а що потрібно знести чи перезаписати. Онови існуючий `seed.md`.

## Крок 3: Інспекція Архітектури та Адаптація (Blueprint Audit)

Замість того, щоб перезаписувати все не глядячи, покроково пройдись по таких пунктах. Якщо пункт вже виконано — йди далі:

1. **`package.json`**: Чи відповідає назва та опис? Чи є необхідні скрипти (`test:all`, `knip`, `audit`)?
2. **`project.md`**: Чи описана архітектура у 5 фаз згідно з **docs/uk/universal-project.md** у фреймворку? Якщо ні — створи або онови цей файл.
3. **Data/Domain Models (Model-as-Schema)**: Чи винесена бізнес-логіка у доменні моделі з метаданими (`static field = { help, default }`)? Проаналізуй всі існуючі форми/сторінки та сформулюй відповідні моделі спільно з користувачем.
4. **Dumb Components (UI)**: Перевір компоненти на наявність хардкоду. Винеси всі тексти та логіки в YAML-дані або моделі. Підключи структуру `/web`.
5. **Continuous Prompts**: Проаналізуй субагентів (якщо вони є в `docs/uk/workflows/` чи `system.md`). Перезапиши їхні промпти під нові задачі проекту (інструкції мають постійно оновлюватись самими агентами).

## Крок 3-B: Жорстка структура директорій (Strict Architecture Layout)

Ти **зобов'язаний** привести проєкт до наступної жорсткої структури:

- `data/` _(або `play/data/`)_: Джерело правди (`.yaml`), переклади (`_/t.yaml`).
- `src/domain/`: Доменна бізнес-логіка, `api/`, `Model-as-Schema` класи. **Жодного UI!**
- `src/ui/`: Компоненти відображення (наприклад, `react-bootstrap/`, `cli/`, `chat/`).
- `src/utils/`: Спільні утиліти (`logger.js`, хелпери, тощо).
- `src/README.md.js` _(або `.jsx`)_: Робочий "Proof-of-Concept" файл, який описує публічне API пакету (використовується для генерації документації та TDD).

> **Чому жорстка структура?** Це зменшує когнітивне навантаження на агентів, дозволяє уникати галюцинацій з приводу розташування файлів та ідеально розділяє Model (Domain) та View (UI).

## Крок 4: Запуск Релізу (MVP) та `next.md`

Ми підходимо до всіх проєктів через структуру релізів (`@nan0web/release`). Відразу створюємо логіку релізу:

1. Створи структуру директорій: `releases/1/0/v1.0.0/`
2. Створи `releases/1/0/v1.0.0/release.md` із повним описом місії та задач по MVP.
3. Створи `.spec.js` файли для логіки у стані `it.todo()`.

`next.md` — це артефакт для трекінгу задач. Додай до нього:

```markdown
# [Назва Пакету] — Поточний Фокус

> **Ціль:** Продовження розробки MVP v1.0.0
> **Актуальний стан:** Реліз та Blueprint (або адаптація) завершено.

## Твої задачі (борг по адаптації або генерації):

1. [ ] Реалізувати `releases/1/0/v1.0.0/domain.spec.js` (Логіка, Model-as-Schema).
2. [ ] Винести хардкод з компонентів у `data/_.nano`.
3. [ ] Налаштувати Snapshot-тести.
```
