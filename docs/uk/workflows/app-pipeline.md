# 🏭 `app-pipeline` (Master Architect Pipeline)

> **Призначення:** Цей workflow є **Великим Майстер-Документом**. Він описує 5-кроковий конвеєр (Pipeline) для "One Logic — Many UI" архітектури та виступає єдиним джерелом істини (Single Source of Truth), яке об'єднує жорстку еталонну структуру та автоматичні перевірки (Zero-Hallucination) на кожному етапі.

## 🏗️ Фундамент: Що ми будуємо? (OLMUI & Model-as-Schema)

Перед стартом конвеєра, Мовна Модель (Agent) повинна усвідомити еталонну структуру, до якої мИ прагнемо під час генерації. Конвеєр будує додаток за таким каркасом:

```text
Папка Додатка/
 ├── .datasets/           автоматично заповниться при індексації додатка (*.md) у векторній базі `nan0ai index` (у .gitignore).
 ├── .husky/              налаштування команд для precommit та інші CI/CD.
 ├── bin/                 бінарні файли додатку.
 ├── data/                (або play/data/) — джерело правди (.yaml). ТУТ зберігаються налаштування та i18n контент додатка.
 │   ├── _/               — Бізнес-логіка, Model-as-Schema класи. ЖОДНИХ UI-фреймворків чи CSS!
 │   │   ├── langs.nan0   — Доступні мови додатку.
 │   │   └── nav.nan0     — Навігація додатку.
 │   ├── en/              — Англійська версія.
 |   ├── uk/              — Українська версія.
 |   └── index.nan0       — Головна сторінка.
 ├── dist/                — Білд додатка (в .gitignore).
 ├── docs/                документація
 │   ├── en/              — Англійська версія.
 │   │   ├── README.md
 │   │   └── user-stories.md  — Сценарії поведінки додатку.
 │   ├── uk/              — Українська версія.
 │   │   ├── README.md
 │   │   └── user-stories.md  — Сценарії поведінки додатку.
 ├── node_modules/        — Залежності додатку (в .gitignore).
 ├── private/             приватні дані (скоріше за все у .gitignore і мають свій окремий git репозиторій).
 │   ├── data/            — файли даних
 │   └── files/           — статичні файли і картинки
 ├── play/                — Робоча область для експериментів.
 ├── releases/            — релізи додатку.
 ├── snapshots/           — снапшоти додатку (*.webp у .gitignore).
 │   ├── cli/             — снапшоти cli додатків
 │   ├── mobile/          — снапшоти mobile додатків
 │   ├── ssg/             — снапшоти ssg додатків (HTML body)
 │   ├── ui/              — снапшоти ui додатків (базовий)
 │   ├── web/             — снапшоти web додатків
 │   │   ├── {locale}/{theme}/{width}/{component_or_fn}.webp
 │   │   └── index.md     — індекс снепшотів, і так само у кожній {locale}/index.md, {locale}/{theme}/{width}/index.md
 │   └── index.md         — індекс снепшотів для генерації snapshots preview
 ├── src/
 │   ├── domain/          — Бізнес-логіка, Model-as-Schema класи. ЖОДНИХ UI-фреймворків чи CSS!
 │   │   ├── index.js     — Точка входу для доменних моделей.
 │   │   ├── *.js         — Модель користувача.
 │   │   └── *.test.js    — Тести для доменних моделей.
 │   ├── test/           — Тести для ре
 │   ├── ui/              — Візуальні компоненти (react, lit, cli), які лише рендерять дані. Жодної логіки.
 │   │   ├── theme.js     — Тема додатку. Використовується для стилізації компонентів.
 │   │   ├── cli/
 │   │   │   └── index.js - точка входу для cli додатків
 │   │   └── lit/
 │   │       └── index.js - точка входу для lit додатків
 │   ├── utils/           — Загальні утиліти.
 │   └── README.md.js     — Документація додатку покрита автоматичними тестами. (provendocs)
 ├── .gitignore           — Файл .gitignore.
 ├── nan0web.nan0         — конфігурація додатку.
 ├── package.json         — конфігурація пакету.
 ├── project.md           — Опис проекту.
 ├── seed.md              — Намір користувача та ТЗ (Генерується на Кроці 1). І видаляється після імплементації.
 ├── tsconfig.js          — Конфігурація TypeScript для додатку тільки для типізації d.ts.
 └── user-stories.md      — Сценарії поведінки додатку.
```

Ця структура **є стандартом NaN•Web додатку**. З якою легко працювати як людині, так і ШІ.

```bash
# Приклад використання
nan0web --dsn data
# Запуск веб документації із markdown файлів
nan0web --dsn docs
# Запуск веб документації зі снапшотів
nan0web --dsn snapshots
```

## 🎭 Актори

- **Архітектор** — Розробник додатків.
- **Агент** — Асистент у редакторі IDE (VSCode, Neovim, тощо) що виконує завдання Архітектора.
- **Клієнт** — Користувач, що надає завдання Архітектору.

## 📡 Покроковий Конвеєр (The 5-Step Pipeline)

Для створення складного додатку без "галюцинацій", мИ розбиваємо процес на 5 ізольованих Субагентів.
**Важливо:** На кожному етапі запускаються детерміновані перевірки.

### 🛠 Крок 1: Аналіз Наміру та ТЗ (The Seed) v0.1.0

- **Workflow:** 🏃‍♂️ `/app-pipeline-01-seed`
- **Дія:** Агент розпитує архітектора, аналізує намір та формує `seed.md` і `user-stories.md`. Створення [release](./release.md) v0.1.0
- **Перевірка:**
  - Архітектор візуально затверджує файл `seed.md` і `user-stories.md`.
  - Фіксація версії тегом.

### 🛠 Крок 2: Доменна Модель (Model-as-Schema) v0.2.0

- **Workflow:** 🏃‍♂️ `/app-pipeline-02-model`
- **Дія:** Генерація JS класів у `src/domain/` з використанням `$schema` + `async *run()`. Жодного UI. Покриття unit-тестами. Створення [release](./release.md) v0.2.0
- **Перевірка:**
  - Всі тести пройшли успішно;
  - Агент зобов'язаний одразу запустити [/inspect-structure](./inspect-structure.md), який підтвердить вірну структуру додатка;
  - Агент зобов'язаний запустити [/inspect-structure](./inspect-structure.md), що створені файли лежать саме в `domain/` і не містять UI-домішок;
  - Архітектор видаляє seed.md.
  - Фіксація версії тегом.

### 🛠 Крок 3: Контрактне Тестування (TDD) v0.3.0

- **Workflow:** 🏃‍♂️ `/app-pipeline-03-contract`
- **Дія:** Створення `*.story.js` для імітації взаємодії користувача з `yield {type: 'ask'}`.
- **Перевірка:**
  - Всі тести пройшли успішно;
  - Агент запускає тести через `node --test` або `bun test`. Тести мають пройти (або вказати на необхідність рефакторингу моделі);
  - Жодного UI-коду. Запускаємо перевірку [/inspect-structure](./inspect-structure.md), [/docs-stories](./docs-stories.md)
  - Фіксація версії тегом.

### 🛠 Крок 4: UI Адаптер (The Pure View) v0.4.0

- **Workflow:** 🏃‍♂️ `/app-pipeline-04-adapter`
- **Дія:** Створення сліпих "Dumb Components" у `src/ui/`. Кольори та стилі беруться **тільки** з загального словника (Design Token Manifest), жодного хардкоду штибу `#ff0000`. Покриваємо тестами.
- **Перевірка:**
  - Всі локальні тести пройшли успішно.
  - Всі попередні тести пройшли успішно.
  - Фіксація версії тегом.

## 🛡️ Щит Від Галюцинацій (The Auditor)

> Якщо на будь-якому кроці конвеєра виникає сумнів щодо того, куди покласти логіку чи інтерфейс, Агент **ПОВИНЕН** виконати скрипт:
>
> ```bash
> 0hcnai inspect arch
> ```
>
> Цей скрипт без LLM проаналізує поточний проект і чітко скаже, чи не порушили ви OLMUI-архітектуру.
