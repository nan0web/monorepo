# ⚖️ Протокол МІри (LLM Operational Boundaries & Anti-Warmup Protocol)

> **Призначення:** Усунути паразитну ентропію «прогріву контексту», обмежити сліпі зони LLM, зберегти час та увагу людини і перевести роботу сесії в детермінований режим: **Один Контракт — Білий Список Файлів — Машинна Верифікація**.

---

## 🧭 Філософія та МІра

LLM — це скальпель для локальних детермінованих трансформацій та контрактного коду, а не зберігач глобальної архітектури.

| 🟢 Де LLM ефективна (Автопілот) | 🔴 Де LLM сліпа (Потрібен Контракт Людини) |
| :--- | :--- |
| **Локальні детерміновані трансформації:** JSON -> AST, RegExp, мапінг полів. | **Утримання глобального інваріанту:** архітектурні шари, межі доменів. |
| **Генерація шаблонного коду за суворим інтерфейсом:** boilerplate, CRUD, конфіги. | **Знання, коли зупинитися:** LLM схильна фантазувати зайве (засмічувати схеми, вигадувати поля). |
| **Закриття TDD контрактів**, коли тест уже зафіксовано людиною/архітектором. | **Вибір глобальної стратегії:** монорепо vs npm, ізоляція доменів. |

## 🏛 4 Закони Тверезої Сесії

```
                   ┌────────────────────────────────────────┐
                   │           ПРОТОКОЛ МІРИ                │
                   └────────────────────────────────────────┘
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        ▼                              ▼                              ▼
 1. RULE OF ONE               2. CONTEXT SANITY             3. TARGET WHITELIST
    CONTRACT                     (≤ 3-4 imports)               (тільки декларовані
 (Red -> Green тест)             (немає "прогріву")              файли + STOP-GATE)
        │                              │                              │
        └──────────────────────────────┼──────────────────────────────┘
                                       ▼
                         4. VERIFICATION BY CODE
                            (pnpm test, 0 failures)
```

### 1. Закон Червоного Контракту (Rule of One Contract)
- Новий чат/сесія починається **не з переказу минулого**, а з одного цільового контракту: `releases/X/Y/vX.Y.Z/task.spec.js` (або `*.story.js`).
- Сесія має єдину мету: перевести контракт зі стану **Red** у стан **Green** за мінімальну кількість кроків.
- Якщо контракту немає — першим кроком формулюється саме він, а не реалізація.

### 2. Закон Автономії Контексту (Context Sanity / No Warmup Trap)
- Для вирішення задачі агенту достатньо 3–4 ключових артефактів:
  1. Доменна Модель / Схема (`*Model.js`).
  2. Інжектований інтерфейс адаптера / DB.
  3. Контрактний тест (`task.spec.js`).
- Якщо агент вимагає читати десятки файлів з різних пакетів, щоб змінити один метод — архітектура протікає. Замість "догріву" сесії слід ізолювати інтерфейс.

### 3. Закон Білого Списку та Зупинки (Target Whitelist & Stop-Gate)
- Перед внесенням будь-яких змін агент зобов'язаний явно задекларувати список цільових файлів:
  ```text
  TARGET_FILES:
  - path/to/file1.js
  - path/to/file2.js
  ```
- **🛑 СУВОРИЙ СТОП-ГЕЙТ (Зовнішні файли):**
  Якщо під час виконання виникає потреба змінити файл, **який не був задекларований у білому списку** (зовнішній модуль, спільний пакет, глобальний конфіг):
  1. Агент **ЗОБОВ'ЯЗАНИЙ НЕГАЙНО ЗУПИНИТИСЯ**.
  2. Заборонено самостійно редагувати цей зовнішній файл.
  3. Агент формулює чітке повідомлення Архітектору:
     - **Який саме файл** потрібно змінити.
     - **Чому** виникла така необхідність (який контракт чи залежність цього вимагає).
     - **Які альтернативи** існують без зачіпання зовнішнього файлу.
  4. Агент чекає явного погодження Архітектора перед продовженням.

### 4. Закон Машинного Свідчення (Verification by Machine)
- Завершення задачі підтверджується виключно чистим виводом команд:
  ```bash
  pnpm run test        # або pnpm run release:spec (0 failures)
  pnpm run test:all    # повний цикл перевірок
  git status           # чистий робочий каталог без побічних змін
  ```
- Жодних суб'єктивних заяв «все готово» без кодового свідчення.
