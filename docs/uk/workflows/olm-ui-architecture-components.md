# OLMUI Архітектура Компонентів та Потік Даних

## 1. Сліпі Компоненти (Blind Components)

В архітектурі **OLMUI (One Logic Multiple User Interfaces)** React-компоненти (та будь-які UI-елементи інших платформ) виступають виключно як «дурні» відображувачі (Renderers). Вони **абсолютно сліпі** до джерела походження даних, які відображають.

### 🚫 Що категорично заборонено в компонентах:
- Прямий імпорт та використання `DBBrowser`, `@nan0web/db-fs`, `DBFS` або `fetch`.
- Складна логіка завантаження даних (наприклад, `useEffect` для запитів на бекенд).
- Жорстке кодування (хардкод) дерев навігації чи масивів даних усередині самого компонента.

### ✅ Кращі практики (Best Practices):
Компонент отримує **готові для відображення дані виключно через `props`** (примітиви, масиви, прості об'єкти) і просто рендерить їх. Кожен компонент має суворий контракт вхідних даних.

```jsx
// src/components/Header.jsx
export default function Header({ navItems, locale, l, onSearch }) {
	// Компонент відображає тільки те, що передано через props.
	// Навіть логіка пошуку делегується через зворотний виклик `onSearch`.
	return (
		<header>
			<nav>
				{navItems.map(item => (
					<a key={item.href} href={item.href}>{item.title}</a>
				))}
			</nav>
		</header>
	)
}
```

## 2. Розробка через Пісочницю (Sandbox-First Development)

Перед тим як компонент інтегрується у головний додаток, він **зобов'язаний** розроблятися та тестуватися у Пісочниці (`sandbox.jsx`). Вона виступає чистим, ізольованим середовищем.

### Функції Пісочниці:
1. **Ізоляція:** Дозволяє розробляти компонент незалежно від бази даних чи глобального стану сторінки.
2. **Документація:** Виступає живою документацією (реєстром компонентів), де видно всі `props`, типи даних та приклади використання.
3. **Єдине Джерело Істини:** Мокові дані у Пісочниці генеруються **виключно через Доменну Модель** (наприклад, через виклик `new Model()`).

```javascript
// src/sandbox.jsx
import { UiMenuModel } from './domain/UiMenuModel.js'
import { Header } from './components/Header.jsx'

// Використовуємо порожній екземпляр моделі для отримання дефолтних значень (mock-даних)
const mockNav = new UiMenuModel().navItems 

export function HeaderDemo() {
	return <Header navItems={mockNav} locale="uk" />
}
```

### Переваги:
Будь-яку проблему компонента можна ізолювати миттєво. Якщо компонент бездоганно працює в Пісочниці, але ламається в додатку — проблема полягає у передачі даних на Верхньому Рівні (Top-Level), а не всередині самого компонента.

## 3. Завантаження Даних на Верхньому Рівні (Top-Level Data Loading)

Якщо компоненти сліпі, хто завантажує дані?
Дані завантажуються **виключно на верхньому рівні (Top-Level Document)** — це `layout.jsx`, `page.jsx` (у Next.js) або `index.jsx` (у Vite SPA).

### Чому саме так?
1. Дані конфігурації, меню та глосарії зазвичай важать лише кілька кілобайт (50-100 KB).
2. Ми можемо дозволити собі почекати ці мілісекунди для завантаження даних і миттєво відрендерити повністю зібраний документ.
3. Це повністю звільняє UI-дерево від каскадних затримок (waterfall loading).

```jsx
// src/app/layout.jsx (Top-Level Document)
import { getDb } from '../db.js'
import { UiMenuModel } from '../domain/UiMenuModel.js'
import Header from '../components/Header.jsx'

export default async function Layout({ children }) {
	// 1. Зчитуємо дані на найвищому рівні через універсальний db.fetch
	const db = await getDb()
	const navData = await db.fetch('nav')
	
	// 2. Пропускаємо сирі дані через Модель для валідації та мапінгу
	const menuModel = new UiMenuModel(navData)
	
	// 3. Передаємо структуровані дані у сліпі компоненти
	return (
		<div>
			<Header navItems={menuModel.navItems} locale="uk" />
			<main>{children}</main>
		</div>
	)
}
```

## 4. Підсумок: Потік Даних в OLMUI

1. **Верхній Рівень (Layout/Page):** Запитує `db.fetch(url)` ➔ отримує об'єкт документа.
2. **Model-as-Schema:** Отримує сирий об'єкт ➔ валідує, застосовує дефолти (або генерує mock-дані для Sandbox через `new Model()`) ➔ повертає чистий структурований об'єкт.
3. **Сліпі Компоненти (UI):** Отримують чисту структуру через `props` ➔ рендерять фінальний HTML.
4. **Sandbox:** Дзеркальне тестувальне середовище для Сліпих Компонентів, яке використовує `new Model()` для генерації даних.

## 5. Моделі та Інтернаціоналізація (i18n) у Компонентах

В архітектурі OLMUI **Доменна Модель (Model-as-Schema)** є єдиним джерелом істини для всіх перекладів та UI-текстів (мітки, підказки, заголовки). Самі компоненти не містять жодних захардкодних перекладів.

### Патерн функції `t` (Translator)

Щоб сліпий компонент міг відображати локалізований текст із Моделі, у нього передається спеціалізована функція перекладу `t`.

Компонент:
1. **Імпортує Модель** (для доступу до статичної схеми).
2. **Приймає функцію `t`** (та поточну `locale`) через `props`.
3. **Використовує `t` у зв'язці зі статичними полями Моделі** для виводу правильного тексту.

### Приклад (Форма чи Віджет):

```jsx
// src/components/SearchWidget.jsx
import { SearchModel } from '../domain/SearchModel.js'

// Компонент отримує `t` через props (від Верхнього Рівня Layout/Page)
export default function SearchWidget({ t, locale, onSearch }) {
	return (
		<div className="search-widget">
			{/* Використовуємо t() передаючи статичне поле схеми Моделі */}
			<label>{t(SearchModel.query.help)}</label>
			
			<input 
				type="text" 
				placeholder={t(SearchModel.query.placeholder)} 
				onChange={(e) => onSearch(e.target.value)} 
			/>
			
			{/* Модель визначає опції та їхні локалізовані мітки */}
			<select>
				{SearchModel.category.options.map(opt => (
					<option key={opt.value} value={opt.value}>
						{t(opt.label)}
					</option>
				))}
			</select>
			
			<button>{t(SearchModel.submitBtn)}</button>
		</div>
	)
}
```

### Чому це важливо?
Завдяки цьому патерну вся текстова структура та словники інкапсульовані у `SearchModel` (Model-as-Schema). Якщо потрібно змінити текст кнопки чи додати нову категорію, ми **редагуємо виключно Модель**, залишаючи React-компонент повністю недоторканим. Компонент виступає чисто механізмом візуалізації (Renderer) для логіки та словника, суворо описаних у Моделі.

## 6. Стандарт Мобільної Навігації (Mobile Bottom Navigation Rule)

> **Критичне UX-правило:** На мобільних пристроях головні елементи навігації, перемикачі мов/тем та кнопки дій **ЗОБОВ'ЯЗАНІ** розміщуватися внизу екрана (`fixed bottom-0 left-0 right-0`), оскільки користувачі утримують смартфон однією рукою і взаємодіють великим пальцем у нижній зоні екрана.

- На десктопі (`md:block`): класичний лівий сайдбар або верхня панель.
- На мобільному (`md:hidden`): нижній зафіксований таббар (`Bottom Navigation Bar`).

## 7. Специфікація Формату OLMUI Документів та Тегування (NaN0 / YAML Syntax)

1. **Компоненти (`<Name>`) vs Налаштування (`$<name>`)**:
   - `$<name>` — означає налаштування / props для компонента або сторінки (наприклад `$content`, `$date`, `$title`, `$Sandbox`).
   - `<Name>` (без префікса `$`) — є ім'ям зареєстрованого OLMUI компонента або HTML-тегу (наприклад `Header`, `PostCard`, `Footer`, `Sandbox`, `content`).

2. **Підтримка подвійного формату передачі props (Dual Prop Format)**:
   - Через префікс `$` на рівні елемента (`$date: Сьогодні`).
   - Через вкладений об'єкт без `$`:
     ```yaml
     PostCard:
       title: Масштабне оновлення оборонного сектору України в 2026 році
       category: war
     $date: Сьогодні
     ```
   - Обидва формати автоматично об'єднуються у пропси компонента: `{ title: "...", category: "war", date: "Сьогодні" }`.

3. **Скорочена форма з простим рядком (Primitive String Value)**:
   - Якщо компонент задано зі строковим значенням:
     `- Header: EA Ukraine Intelligence`
     `- Footer: © 2026 Euro-Atlantic Ukraine.`
   - Рядок автоматично передається як первинний проп або `children`.

4. **Абсолютна заборона `if (Component)` у коді системних рендерів**:
   - Жодних умовних конструкцій типу `if (input.$Sandbox)` у `ServerElement` чи `UIReact`.
   - Будь-який компонент (включаючи `Sandbox`) рендериться суто через загальний алгоритм співставлення зареєстрованого тегу `components[type]`.

## 8. Поліморфний Протокол Бази Даних (`this._.db`) та Layout Engine (`Content: true`)

1. **Єдиний метод зчитування `db.fetch(url)`**:
   - Моделі, додатки та роутери **НІКОЛИ** не використовують файловий модуль `fs` або відносні HTTP `fetch` напряму. Зчитування виконується виключно через:
     ```javascript
     const doc = await this._.db.fetch(url) // або await db.fetch(url)
     ```
   - **На сервері (SSR / SSG / RSC)** використовується драйвер `@nan0web/db-fs` (DBFS).
   - **На клієнті (Browser / PWA)** використовується драйвер `@nan0web/db-browser` (DBBrowser), який зчитує статичні `.json` маніфести, скомпільовані під час SSG.

2. **Спадкування глобального макета (`_/$content.nan0`) та Плейсхолдер `Content: true`**:
   - Глобальний макет додатка зберігається в `data/_/$content.nan0`:
     ```yaml
     - Header: true
     - Content: true
     - Footer: true
     ```
   - Вузол `Content: true` (або `Content`) є спеціальним системним плейсхолдером, замість якого `ServerElement` та `ClientPreview` рекурсивно рендерять масив `doc.content` конкретної сторінки (`index.nan0`).
   - Якщо сторінка вказує власний `$content: - Content: true` (як у `sandbox.nan0`), вона перевизначає глобальний шаблон і малює тільки свій `content:` (`Sandbox`).
