# 📖 User Stories — Workflow Usage Patterns

> Приклади використання workflow для типових сценаріїв розробки в екосистемі nan0web.

**Як і де це використовується:**
1. **Точка входу (Orchestration):** Головний маршрутизатор для комплексних задач (створення додатку, реліз).
2. **Економія контексту:** Агент підвантажує лише ті workflow, які необхідні на поточному кроці сценарію.
3. **Навчання субагентів:** Передача конкретних кроків сценарію субагентам для виконання автономних задач.
4. **Довідник архітектора:** Шпаргалка для розробника щодо послідовності пайплайнів у розробці "Nan0web way".

> **Універсальна підтримка:** Цей стандарт та описані пайплайни розроблено для роботи в будь-якому AI-середовищі — **Antigravity**, **LLiMo App**, **VSCode Copilot** та **VSCode Continue**.

## 🆕 Сценарій 1: Створення нового додатку з нуля

**Контекст:** Архітектор хоче створити новий додаток `bank.app` з повним циклом розробки.

### Крок 1: Аналіз наміру (The Seed)

```
Архітектор: "Створи новий додаток bank.app із детальним поясненням функціоналу"
Агент читає: app-pipeline-01-seed.md
Агент розбиває запит на задачі
Агент запитує по кожній задачі у knowledge-base (або в інструментах mcp-knowledge-base) і отримує відповідь з файлами і проєктами де вже інтегровані схожі рішення, які він збирає для написання структури проєкту.
Агент: Створює seed.md + user-stories.md.
Агент: Створює незалежний від платформи project.md (наприклад, у docs/uk/project.md)
Агент: Інспектує створений намір та документацію на відповідність архітектурним стандартам.
Архітектор: Затверджує ТЗ
```

### Крок 2: Фізична Ініціалізація та Архітектура

```
Агент читає: init-project.md (або відповідний крок пайплайну)
Агент: Визначає цільову платформу на основі наміру (за замовчуванням — JavaScript екосистема)
Агент: Використовуючи seed.md, створює базову структуру директорій (src/domain, data/ тощо)
Агент: Генерує конфігураційні файли залежно від платформи (package.json тощо)
Агент: Обов'язково створює nan0web.nan0 — конфігурацію агента для цього додатку (задає інспекторів та workflows)
Агент: Встановлює базові залежності (pnpm install)
```

### Крок 3: Доменна модель

```
Агент читає: app-pipeline-02-model.md, model-schema.md
Агент: Створює src/domain/{CardModel,DepositModel,TransferModel}.js
Агент читає: inspect-structure.md, inspect-models.md
Агент: Запускає перевірки — структура вірна, моделі відповідають стандарту
```

### Крок 4: Контрактні тести

```
Агент читає: app-pipeline-03-contract.md
Агент: Створює *.story.js для кожного сценарію
Агент читає: test-style-scanner.md (інспектує написані тести)
Агент: Запускає тести — всі пройшли
```

### Крок 5: UI Адаптери (Core)

```
Агент читає: app-pipeline-04-adapter.md
Агент: Створює базові UI адаптери в src/ui/
Агент читає: olm-ui-architecture-adapters.md
```

### Крок 6: UI-CLI Інтерфейс

```
Агент читає: app-pipeline-05-ui-cli.md
Агент: Реалізує CLI інтерфейс
Агент читає: cli-gallery.md (інспектує CLI)
```

### Крок 7: UI-Chat Інтерфейс

```
Агент читає: app-pipeline-06-ui-chat.md
Агент: Реалізує Chat інтерфейс
```

### Крок 8: UI-Web Інтерфейс

```
Агент читає: app-pipeline-07-ui-web.md
Агент: Реалізує Web інтерфейс
Агент читає: inspect-web.md
```

### Крок 9: UI-Mobile Інтерфейс

```
Агент читає: app-pipeline-08-ui-mobile.md
Агент: Реалізує Mobile інтерфейс
```

### Крок 10: QA та реліз

```
Агент читає: app-pipeline-09-qa.md
Агент: Винесе всю статику в data/uk/_/t.yaml
Агент читає: i18n-builder.md
Агент: Запускає npm run test:all
Агент читає: release.md → створює release v1.0.0
```

**Використані workflow:** 12 файлів

## 🔧 Сценарій 2: Внесення змін в існуючий пакет

**Контекст:** Треба додати нове поле `currency` в `CardModel`.

### Крок 1: Аналіз впливу

```
Архітектор: "Додай поле currency в CardModel"
Агент читає: inspect-anti-pattern.md (перевірити чи не ламає архітектуру)
Агент: Аналізує поточну модель
```

### Крок 2: Зміна моделі

```
Агент читає: model-schema.md
Агент: Додає static currency = { help: '...', type: 'string', default: 'UAH' }
Агент: Додає /** @type {string} */ this.currency в конструктор
```

### Крок 3: Оновлення тестів

```
Агент читає: fix.md (Red-Green-Refactor)
Агент: Оновлює тести для нового поля
Агент: Запускає npm test
```

### Крок 4: Оновлення UI

```
Агент читає: ui-update.md
Агент: Перевіряє чи UI адаптери коректно рендерять нове поле
Агент читає: interface-welding.md → оновлює контракти
```

### Крок 5: Перевірка

```
Агент читає: inspect-models.md → перевірка моделі
Агент читає: inspect-i18n.md → перевірка перекладів
Агент: Запускає npm run test:all
```

**Використані workflow:** 7 файлів

## 🐛 Сценарій 3: Виправлення багу

**Контекст:** Користувач повідомив що CLI не показує помилку валідації.

### Крок 1: Відтворення

```
Архітектор: "CLI не показує помилку валідації email"
Агент читає: fix.md (Red-Green-Refactor)
Агент: Створює тест який репродукує баг (Red)
```

### Крок 2: Діагностика

```
Агент читає: inspect-structure.md (перевірити архітектуру)
Агент читає: code-style.md (перевірити стиль коду)
Агент: Знаходить проблему — помилка не yield-иться в CLI адаптер
```

### Крок 3: Виправлення

```
Агент: Фіксить код — додає yield log('error', ...)
Агент: Запускає тест — тепер проходить (Green)
```

### Крок 4: Рефакторинг

```
Агент читає: test-fast.md (перевірити чи тести швидкі)
Агент: Оптимізує тести якщо потрібно
Агент читає: commit.md → безпечний коміт
```

**Використані workflow:** 5 файлів
