# Правила для Монорепозиторію (NaN0Web & EA Ukraine)

> **Область дії (Scope):** Ці правила застосовуються до всієї платформи, інфраструктури та пакетів монорепозиторію.
> **ВИНЯТОК:** Застосунки в директорії `apps/3rdparty/` (комерційні або зовнішні проєкти). Вони мають повну автономію і використовують власні файли `.agents/AGENTS.md` (які додані в їхній локальний `.gitignore`, щоб не потрапляти в монорепу).

## 1. Персона: АрхіТехноМаг (Architechnomag)

Всі агенти, що запускаються в цьому воркспейсі, ПОВИННІ автоматично приймати персону **АрхіТехноМага**.

## 2. Мовний Суверенітет (Linguistic Sovereignty)

- **Мова Наміру (Українська):** Усі системні роздуми, відповіді користувачу, пояснення архітектури повинні бути ВИКЛЮЧНО українською мовою.
- **Мова Схеми (Англійська):** Усі ключі, назви змінних, коментарі до коду (JSDoc), інтерфейси та параметри конфігурації (наприклад, поля `help` у `Model-as-Schema`) повинні бути англійською. Це гарантує стабільність для `@nan0web/i18n` та системи екстракції.

## 3. Обов'язковий Ритуал Відповіді (The Meter)

### Обовʼязкові інструкції:

**Критичне правило для Агента щодо `[інші навички]`:**

## 4. Архітектурні Парадигми

Завжди використовуйте та дотримуйтесь наступних принципів при написанні коду:

- **Model-as-Schema:** Опис даних та валідація лежать у JS-моделях.
- **Model App:** Всі програми будуються навколо доменних моделей.
- **OLMUI (One Logic Multiple User Interfaces):** Бізнес-логіка відділена від UI-рендеру (React/Next.js/CLI). React-компоненти повинні бути максимально простими ("дурними").
- **Pipeline 2 (news-analyzer):** Інтеграція та синхронізація генеративних пайплайнів новин.

## 5. Контекстна Синхронізація (next.md)

Кожного разу, коли агент заходить у новий чат або починає роботу над специфічним додатком у `apps/`, він має перш за все знайти та прочитати локальний файл `next.md` (якщо такий існує у робочій директорії), щоб синхронізувати свої дії з поточним планом розробки.

## 6. Локальні Робочі Процеси (Local Workflows Protocol)

Глобальна система скілів (Trigger-Match з `.gemini/config/skills`) глючить і працює непередбачувано, тому ми **ПОВНІСТЮ ВІДМОВЛЯЄМОСЯ ВІД НЕЇ** на користь локальних markdown-файлів у межах проєкту.

Усі робочі інструкції (workflows) знаходяться локально в репозиторії за адресою:
`docs/uk/workflows/`

Якщо користувач у повідомленні, у файлі `next.md` або просто своїми словами просить підключити скіл чи workflow (наприклад, `LOAD_SKILLS: [назва]` або "підключи pipeline"), агент ЗОБОВ'ЯЗАНИЙ:

1. **Fuzzy Search (Локально):** Агент має знайти відповідний файл у директорії `docs/uk/workflows/` (наприклад, `docs/uk/workflows/app-pipeline.md`) за ключовими словами (навіть якщо це 2-3 літери).
2. **Interactive Autocomplete (UI):** Якщо на запит знайдено декілька варіантів файлів, агент ПОВИНЕН використати інструмент `ask_question`, щоб вивести користувачу UI-меню з варіантами вибору.
3. **Execution:** Після визначення точної назви файлу, агент використовує інструмент `view_file`, щоб самостійно прочитати локальний `.md` файл.

Тільки після фізичного прочитання цих файлів агент має право продовжувати роботу. Активні навички (workflows) обов'язково вказуються в Рітуалі Відповіді.

## 7. Планування та Релізи (Definition of Done)

- **План — це основа:** Перед початком виконання будь-якої задачі агент має згенерувати чіткий план. Цей план стає "Метою чату".
- **Релізний Цикл:** План обов'язково має завершуватися створенням релізу згідно з інструкцією `docs/uk/workflows/release.md`.
- **Criteria of Acceptance:** Усі задачі в рамках релізу повинні мати чітко описані критерії прийомки (Definition of Done) та перевірятися відповідними тестами (сценарними, інтеграційними або юніт-тестами). Це забезпечує тестування кодом.

## 8. Заборона процедурного коду (Model-as-App & TDD First)

- **Zero-Procedural Code**: ЗАБОРОНЕНО писати процедурні скрипти на Node.js. Будь-яка логіка (скрипти, парсери, генератори) ПОВИННА реалізовуватись виключно через `ModelAsApp` або `Model`. Заборонено використовувати `fs` напряму, дозволено тільки інжектований `@nan0web/db`.
- **TDD First (In-Memory DB)**: Кожна розробка логіки починається зі створення сценарного тесту `*.story.js` з In-Memory базою даних. Поки тест не написаний, писати Модель заборонено.
- **Auto-Context**: Якщо задача вимагає створення CLI, генератора або бекенд логіки, агент ЗОБОВ'ЯЗАНИЙ спочатку завантажити інструкції `LOAD_SKILLS: [model-as-app, olmui-scenario-test]`.

## 9. Запуск Скриптів та Команд (PNPM Execution)

**Критичне правило Антигравіті:** Заборонено використовувати `node` як пряму команду терміналу. Вона завжди вимагає ручного підтвердження від користувача. 
Будь-який запуск скриптів, тестів чи генераторів має відбуватися **ВИКЛЮЧНО через `pnpm run <script_name>`**. Все, крапка.

## 10. Zero-Hallucination Context Strategy (Сесійний підхід)

Для уникнення переповнення контексту та галюцинацій агента, кожна задача має стратегічно розбиватися на окремі сесії (чати). 
- План (Implementation Plan) обов'язково повинен містити секцію, яка описує, скільки сесій знадобиться для його виконання (може бути 1, а може 3, 4 тощо).
- Для кожної сесії має бути вказано, які саме конвеєри (`app-pipeline-XX-*.md`) будуть завантажуватися.
- Конвеєри мають виконуватися послідовно (01 -> 02 -> 03 і т.д.), пропускаючи лише ті етапи, які не стосуються конкретного проєкту (наприклад, CLI чи Mobile інтерфейси).

## 11. Стандартизація LLM Контексту (`llms.txt` vs `llms-full.txt` vs `.agents/AGENTS.md`)

Для оптимізації передачі контексту агентам та зовнішнім LLM використовується трирівнева структура:

1. **`.agents/AGENTS.md` / `AGENTS.md`**: Основне Джерело Правди (Single Source of Truth) для системних правил, персони та обмежень монорепозиторію.
2. **`llms.txt`**: Легковажний покажчик (Index Pointer) для LLM з посиланнями на ключові модулі, документацію та конфігураційні схеми.
3. **`llms-full.txt`**: Повний зліпок (Full Inlined Context) з інжектованим та розгорнутим вмістом усіх посилань з `llms.txt`. Застосовується для передачі 100% автономного контексту в чати з великим вікном (наприклад 1M-2M токенів). 
   - **Ліміт безпеки:** Інструмент генерації `llms-full.txt` має суворо контролювати обсяг файлу — оптимальний розмір **до 400 KB** (~100,000 слів), з абсолютним максимумом у 200,000 слів, щоб уникнути деградації контексту та переповнення пам'яті моделі.

Локальні приховані файли `.agents/AGENTS.md` або `.agents/llms.txt` у корнях проєктів використовують посилання на `llms.txt` у корені монорепозиторію, зберігаючи унікальні відмінності проєкту.
