## 🎯 1. Архітектура Навігації (CLI + Web)

Ми відмовляємося від дублювання логіки роутингу для терміналу і браузера. Беремо найкраще з підходів Next.js (File-System Routing) та адаптуємо під OLMUI.

**Єдине джерело істини:** `data/_/nav.nan0`

```yaml
# data/_/nav.nan0
- href: /
  title: Home
- href: docs
  title: Documentation
```

### Як це працює з мінімумом сутностей:
* **Локалізація**: `href` у `nav.nan0` не містить мови (наприклад, `href: docs`). Роутер `PagesRouter` автоматично доповнює шлях поточною локаллю (`data/{locale}/docs.nan0`). При перемиканні мови контент просто береться з іншої папки.
* **Web версія**: `PagesRouter` читає `nav.nan0` для побудови сайдбару/меню. При кліку завантажується відповідний `.nan0` файл.
* **CLI версія**: `ShellModel` читає `nav.nan0` і будує інтерактивне дерево. При виборі сторінки CLI завантажує `.nan0` файл та рендерить його через `ContentViewer`. 
* **Складні дії (напр., `build`)**: Звичайні сторінки працюють автоматично через файлову систему, але для технічних операцій ми можемо зберігати `ModelAsApp` з `static command`. Якщо введено `nan0web build` — CLI напряму викликає цю команду з `ShellModel` (оминаючи навігацію). Тобто, роутинг розділяється: `контент -> File System`, `дії -> Commands`.

## 🎯 2. Архітектура Snapshot-тестів

Зліпки тестують послідовність OLMUI-інтенцій (Intents), які повертає генератор. Щоб тест був детермінованим, він має чітко вказувати, **що запускає генератор** (trigger/input) та **які відповіді дає користувач** (якщо це `ask`).

**Формат зліпка (`test/snapshots/docs.nan0`):**
Для лаконічності використовуємо масив, де **першим елементом** завжди йде об'єкт ініціалізації (`input` або `trigger`), а далі — очікувані інтенції.

```yaml
# 1. Тригер (Перший елемент масиву)
- input:
    command: docs
    args: { path: "README" }
    answers: [] # Імітація відповідей (опційно)

# 2. Очікувана послідовність (наступні елементи)
- progress:
    message: "Loading docs..."
- render:
    component: "ContentViewer"
    props: { title: "Documentation" }
- result:
    ok: true
```

*Такий підхід ідеально лягає на логіку генераторів: перший елемент запускає генератор, а наступні — перевіряють кожен крок `yield`.*

## 🎯 3. Автовизначення UI та Конфігурація

Замість набору розрізнених булевих прапорців (`cli: true`, `web: true`), конфігурація UI повинна бути масивом або множиною (Set), що точно відповідає експортам у `package.json`.

**Файл конфігурації `nan0web.nan0` (Мінімум):**
```yaml
# yaml-language-server: $schema=schemas/NaN0WebConfig.schema.json
ui:
  - cli
  - web
```

**Логіка раннера (`src/runner.js`):**
Якщо властивість `ui` не вказана у конфігу, раннер автоматично зчитує `package.json` та формує масив доступних інтерфейсів на основі експортів:
```javascript
if (!config.ui || config.ui.length === 0) {
    const pkg = await db.fetch('package.json');
    const exports = pkg.exports || {};
    // Шукаємо експорти виду "./ui/cli", "./ui/web"
    config.ui = Object.keys(exports)
        .filter(k => k.startsWith('./ui/'))
        .map(k => k.replace('./ui/', ''));
}
```
