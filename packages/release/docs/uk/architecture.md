# Архітектура PM-as-Code Релізу (@nan0web/release)

> **Статус:** Архітектурний стандарт (v3.7.0)  
> **Область дії:** Структура релізів, беклог, маніфести `_.nan0`, `config.nan0`, паспорти версій та статуси

---

## 1. Світовий ландшафт та Єдине Джерело Правди (Single Source of Truth)

Сучасні інструменти управління проєктами та релізами (Backlog.md, Changesets, ADR, Git-Native репозиторії) спираються на чітке розмежування між **глобальним пулом намірів** та **зафіксованим скоупом версії**:

| Складова | Канонічне розташування | Призначення та поведінка |
| :--- | :--- | :--- |
| **Глобальний беклог (Файл)** | `<releasesDir>/backlog.md` | Глобальний єдиний вхідний файл нерозподілених задач, ідей та вимог на рівні всього проєкту. |
| **Глобальний беклог (Каталог)** | `<releasesDir>/backlog/` | Модульний каталог беклогу, де кожна велика ідея/фіча може бути окремим `*.md` документом. Точка входу — `backlog/README.md` або `backlog/index.md` (для перегляду на GitHub/GitLab). |
| **Каталог релізу версії** | `<releasesDir>/X/Y/vX.Y.Z/` | Фіксований скоуп конкретного релізу: паспорт завдань (`task.md` / `release.md` / `README.md`), контрактні тести (`task.spec.js`) та метрики виконання (`user.md`). |

### ⚠️ Антипатерн локального беклогу:
Розміщення `backlog.md` усередині версійного каталогу (`<releasesDir>/X/Y/vX.Y.Z/backlog.md`) суворо заборонено:
- **Чому це порушення:** Версійний каталог відповідає за зафіксовані зобов'язання (Definition of Done) конкретного релізу. Наявність незавершеного локального "беклогу" всередині релізу ламає автоматичний розрахунок готовності (RRS) та породжує хаос при передачі контексту агентам.
- **Діагностика аудитора:** Якщо виявлено `backlog.md` у версійному каталозі, `ReleaseAuditor` та `CheckCommand` фіксують порушення `MISPLACED_BACKLOG` (рівень `warning` або `error` за налаштуванням).

## 2. Гнучкість формату паспортів версій (task.md, release.md, README.md)

Для зручності читання та інтеграції з веб-інтерфейсами (GitHub, GitLab, веб-портали) каталог версії підтримує синоніми головного паспорта завдань:
1. `task.md` — канонічний PM-as-Code паспорт завдань із FrontMatter (пріоритет для AI-агентів).
2. `release.md` — людино-орієнтований опис релізу та чеклист.
3. `README.md` — стандартний файл перегляду, що автоматично відображається у вебі репозиторію.

Сканер та аудитор сприймають будь-який із цих файлів як валідний опис релізу.

## 3. Модульний беклог (Backlog Directory)

Якщо беклог проєкту стає занадто великим для одного монолітного файлу `backlog.md`, він організовується як директорія:
```text
releases/
├── README.md                     # Огляд усіх релізів проєкту (з мітками releases:status)
├── backlog.md                    # Єдиний беклог (варіант А)
│   або
├── backlog/                      # Модульний беклог (варіант Б)
│   ├── README.md                 # Індексний огляд беклогу для Git-інтерфейсів
│   ├── auth-enhancements.md      # Окремий епік / задача
│   └── payment-gateway.md        # Окремий епік / задача
├── _.nan0                        # Data-driven вітрина (ReleaseStatusView: true)
├── config.nan0                   # Data-driven конфігурація ($access: role admin)
└── 3/7/v3.7.0/                   # Каталог релізу (тільки зафіксований скоуп)
    ├── README.md (або task.md)   # Паспорт релізу
    ├── task.spec.js              # Контрактні тести (TDD)
    └── user.md                   # Метрики та фідбек Архітектора
```
Обидва варіанти (`backlog.md` та `backlog/`) є повноправними громадянами архітектури релізів і не вважаються "сирітськими" файлами (orphan files).

## 4. Автоматична Генерація Статусів у `releases/README.md` (`nan0release status -w`)

Файл `releases/README.md` містить спеціальні маркери:
```markdown
# Releases

<!-- releases:status:start -->
<!-- releases:status:end -->
```

При виконанні `nan0release status -w` (прапорець `--write`):
1. `Scanner.status()` сканує каталог релізів та отримує актуальний список версій, контрактів, регресійних тестів та текстових документів (`task.md`, `release.md`, `user.md`).
2. Генерується таблиця з **відносними посиланнями** від каталогу `releases/` до всіх ресурсів:
   ```markdown
   | Версія | Статус | Контракт | Регресія | Документи |
   | :--- | :--- | :--- | :--- | :--- |
   | [**v3.7.0**](3/7/v3.7.0/) | 🟡 Active (WIP) | [`task.spec.js`](3/7/v3.7.0/task.spec.js) | — | [task.md](3/7/v3.7.0/task.md), [user.md](3/7/v3.7.0/user.md) |
   | [**v1.0.3**](1/0/v1.0.3/) | 🟢 Closed | — | [`task.test.js`](../src/tests/releases/1/0/v1.0.3/task.test.js) | [task.md](1/0/v1.0.3/task.md) |
   ```
3. Вміст між коментарями замінюється на таблицю зі збереженням самих коментарів для наступних генерацій.
